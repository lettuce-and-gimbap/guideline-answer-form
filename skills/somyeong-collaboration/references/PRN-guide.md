# PRN | 작업 과정과 결과 설명 지침

## 작업 중에 남길 것

- 기획할 때 결과에 영향을 주는 조건의 근거를 남긴다. 과제 문구나 자료의 위치, 담당자 확인, 사용자 결정, 임시 가정 중 어디서 나온 조건인지 표시한다. 근거가 부족한 조건은 가정으로 두고, 확인되거나 바뀌면 반영한 이유를 기록한다.
- 구현 방향을 정하거나 바꿀 때는 **무엇을 선택했는지 → 왜 그렇게 했는지 → 사용자에게 어떤 차이가 있는지** 한두 문장으로 남긴다. AI 제안을 반영·수정한 경우 실제 제안과 변경 이유를 적는다. 사용자와 AI가 각각 한 일을 확인할 수 있는 범위에서 구분한다.
- 검증할 때는 **조건 → 입력·확인 순서 → 기대한 결과 → 실제 관찰한 결과**를 남긴다. 확인한 화면·파일·명령 중 재현에 필요한 것만 적는다. 못 한 검사는 미확인으로 표시한다.

## 사용자 설명과 제출 문서에 담을 일곱 항목

| 항목 | 설명할 내용 |
| --- | --- |
| 1. 작업 과정과 기능 | 무엇을 해결하려 했고, 어떤 순서로 작업했는지 설명한다. 핵심 기능마다 사용자가 무엇을 넣거나 누르면 어떤 결과가 나오는지 적는다. 방향이 바뀌었다면 결정에 영향을 준 이유를 포함한다. |
| 2. 언어와 도구 | 실제 사용한 언어와 실행에 필요한 도구를 적는다. 각각 어떤 역할을 맡았고 과제 조건에 왜 맞았는지 짧게 설명한다. |
| 3. 조건에 맞게 작동하는지 확인 | 핵심 조건마다 사용자가 따라 할 수 있는 입력과 순서, 기대값, 실제 관찰값을 연결한다. 계산값에는 단위와 필요한 경우 기준값·분모를 적는다. 저장·재열기·내보내기가 필수라면 해당 결과까지 확인한다. |
| 4. 예외가 발생했을 때 | 결과나 기존 데이터를 바꿀 수 있는 예외부터 고른다. 실제로 어떤 안내나 처리가 일어났고, 기존 상태가 유지됐는지 확인한다. 아직 실행하지 않은 경우에는 예상 동작이라고 표시한다. |
| 5. 결과물로 확인할 수 없는 것 | 구현 범위 밖의 기능, 실행하지 못한 검사, 현재 데이터로 판단할 수 없는 효과를 구분해 적는다. 확인하려면 무엇이 필요한지 덧붙인다. |
| 6. 데이터가 늘 때 생길 문제 | 영향이 큰 지점부터 **어떤 데이터가 늘 때 → 어디에 일이 몰리는지 → 어떤 증상으로 보일지 → 판단 근거** 순서로 쓴다. 근거는 반복 조회, 전체 파일 읽기, 항목 간 비교처럼 실제 코드나 자료에서 찾는다. 실측했다면 데이터 규모·실행 환경·측정값을 함께 적고, 코드로 추정했다면 측정할 항목을 제안한다. |
| 7. 요구사항을 확정한 근거 | 중요한 조건을 무엇을 보고 정했는지 적는다. 확인된 조건과 직접 선택한 구현 규칙을 구분하고, 임시 가정이 바뀌면 영향을 받는 기능을 설명한다. |

## 전달 방식

질문에 바로 답하고 실행에 필요한 첫 입력, 예상 화면이나 결과, 다음 행동을 순서대로 알려준다. 기술 용어가 필요하면 첫 등장에 쉬운 뜻을 덧붙인다. 사용자가 직접 해보려면 어떤 버튼을 누르거나 어떤 파일을 열고 무엇을 보면 되는지 말한다.

과제에서 지정한 문서명·질문·분량이 있으면 그 형식에 맞춰 해당 내용을 넣는다. 별도 제출 문서가 필요하지 않으면 대화에서 요약한다. 작은 작업이나 데이터 규모와 무관한 작업에는 관련 항목만 사용한다. 실행하지 않은 검사, 측정하지 않은 성능, 참여하지 않은 사람의 판단을 사실로 기록하지 않는다.
